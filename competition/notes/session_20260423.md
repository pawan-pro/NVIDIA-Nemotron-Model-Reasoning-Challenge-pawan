## What was attempted today

### 1. Tiny SFT notebook branch

A cloned notebook was created to run a very small supervised fine-tuning experiment.

Initial tiny-SFT design:

* 500-row subset
* 1 epoch
* LoRA rank 32
* target answers formatted as `\boxed{answer}`

### 2. First training path: custom HF `Trainer`

A custom Hugging Face training path was attempted.

This led to several sequential blockers:

* `cutlass` / `mamba_ssm` import issues
* `TrainingArguments` API mismatch
* `Trainer(..., tokenizer=...)` API mismatch
* Triton / `ptxas-blackwell` permission failures during training-time kernel compilation

### 3. Runtime/environment investigation

The official metric notebook and competition files were reviewed.

Important findings:

* the official metric notebook copies the NVIDIA utility stack to `/tmp` and `chmod +x` the Triton PTXAS binaries before execution 
* that setup is sufficient for the **metric inference path**, but our custom full-model training still hit Mamba/Triton training kernels and failed
* the competition only requires a valid compatible LoRA adapter zip, not any specific training framework 

### 4. Attempted pivot to `trl.SFTTrainer`

A second path based on the previous Nemotron SFT notebook was considered.

This was blocked by environment constraints:

* `trl` is **not installed**
* internet **cannot be enabled** for this competition with the current accelerator
* current notebook environment is pinned and dependency-constrained

### 5. Environment reality check

Screenshots confirmed:

* internet cannot be enabled for this competition with the current accelerator
* current runtime shown in the active session is **GPU T4 x2**
* pinned/original environment is in use
* dependency manager exists, but we do not have evidence yet that it can supply `trl` offline from cache

This means the original plan of “quick tiny SFT in this notebook” is **not currently viable**.

---

## What was learned

### 1. The core blocker is environment mismatch, not just code bugs

Today’s failures are not random syntax issues. They come from trying to do Nemotron Mamba/Triton training in a constrained Kaggle environment that:

* lacks `trl`
* blocks internet
* has accelerator-dependent restrictions
* keeps routing into brittle Triton training kernels

### 2. The official metric notebook is useful for inference/runtime setup, not as proof that training will work

The metric notebook demonstrates:

* environment bootstrap
* model loading
* vLLM inference
* boxed-answer extraction
  but **not** a robust tiny-SFT path 

### 3. Prompt/formatting still matter a lot

The metric explicitly prioritizes answers inside `\boxed{}` and falls back heuristically otherwise .
So prompt-only evaluation remains a high-value low-risk path.

### 4. Baseline notebook must remain frozen

Because the final submission requirement is strict and packaging already works, the known-good baseline notebook should stay untouched as the fallback valid artifact path .

---

## Main decision from today

**Do not keep patching the current SFT notebook for training.**

Instead:

### Pivot to an offline prompt-eval notebook

A new offline evaluation notebook was drafted in **3 code blocks** to:

* use the available Nemotron base model
* compare multiple prompt variants
* extract answers with metric-aligned logic
* measure exact-match accuracy on a fixed train subset
* identify the best boxed-answer prompt template

This is the safest next experiment under current constraints.
